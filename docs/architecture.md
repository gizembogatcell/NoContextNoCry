## MoSCoW Prioritization (2-hour budget)

### MUST HAVE (~70 min) — Demo-critical, non-negotiable

- **Retro Board CRUD** (15 min) — Create/list/get retros with Mad/Sad/Glad columns, stored in MongoDB
- **Sticky Note Cards** (15 min) — Add anonymous cards to a column, display in a Kanban-style board
- **Phase Flow: Write -> Vote -> Actions** (15 min) — Moderator controls phase transitions; UI adapts per phase
- **Dot Voting** (10 min) — Each participant gets N votes, click-to-vote on cards
- **Card-to-Action conversion** (10 min) — One-click convert a card to an action item with owner + deadline
- **AI Retro Summary** (5 min) — Send all cards to existing AI proxy, get themes + action suggestions

### SHOULD HAVE (~30 min) — High value, build if MUST is done

- **Team Board** (10 min) — Dashboard showing all open action items across retros
- **AI Grouping** (10 min) — AI clusters similar cards and suggests group titles
- **Retro Memory Screen** (10 min) — "X actions still open from last retro" warning at retro start

### COULD HAVE — Nice polish, defer if tight

- **Timer for write phase** — Countdown timer the moderator can set
- **AI Chat Sidebar** — Full conversational AI panel (frontend only, backend exists)
- **Card anonymity toggle** — Show/hide author names per phase

### WON'T HAVE (this hackathon)

- **Email notifications (Resend)** — External service setup, not demo-critical
- **Jira integration** — OAuth/token flow too slow for 2h
- **Real-time collaboration (WebSocket)** — Adds infra complexity; polling or manual refresh is fine
- **Drag-and-drop grouping** — Complex DnD lib integration; manual group-assign is enough

## Decisions

### Client-only auth (no middleware) — KEPT

Firebase auth state lives entirely in the browser via `AuthProvider`. Protected routes use a client-side guard in `(app)/layout.tsx` that redirects to `/login` when unauthenticated. API routes verify tokens server-side via `requireUser()`. This avoids cookie/session complexity and keeps the auth flow transparent.

### Single ConfigProvider for theming — KEPT

All Ant Design tokens are centralized in `src/theme/antd-theme.ts` and applied through a single `ConfigProvider` in `src/app/providers.tsx`. No nested providers.

### Service layer separation — KEPT

API routes (`src/app/api/`) handle HTTP concerns only (parsing, auth, response formatting). Business logic lives in `src/services/` with `server-only` imports to prevent accidental client bundling.

### Standardized API responses — KEPT

All API routes return `{ data }` on success or `{ error: { message, code, details? } }` on failure via helpers in `src/lib/api/response.ts`.

### Cards in separate collection (NEW)

Cards are stored in their own MongoDB collection (`cards`) rather than embedded in the retro document. This avoids rewriting the entire retro doc on every vote toggle and allows efficient per-card updates.

### Actions as standalone collection (NEW)

Actions have their own collection with a `retroId` reference. This enables the Team Board to query open actions across all retros efficiently, and supports the carry-over feature (moving unfinished actions to new retros).

### Phase-driven UI + server guards (NEW)

The `phase` field on the retro document (`write | vote | actions | closed`) controls both what the UI renders and what mutations the server allows. For example, adding cards is only allowed during `write` phase; voting is only allowed during `vote` phase. The moderator (retro creator) advances phases.

### AI reuses existing proxy (NEW)

All AI features (summarize, grouping, chat) call the existing `callAiProxy()` function. The only new code is retro-specific prompt engineering in `retro-ai.service.ts`. No new env vars or infrastructure needed.

## Data Model

Four MongoDB collections:

### `retros`

```typescript
type RetroPhase = "write" | "vote" | "actions" | "closed";
type RetroTemplate = "mad_sad_glad";

type Retro = {
  id: string;
  teamId: string;          // optional team scoping
  title: string;
  template: RetroTemplate;
  phase: RetroPhase;
  votesPerUser: number;     // default 3
  createdBy: string;        // uid — acts as moderator
  createdAt: string;
  updatedAt: string;
};
```

### `cards`

```typescript
type CardColumn = "mad" | "sad" | "glad";

type Card = {
  id: string;
  retroId: string;
  column: CardColumn;
  content: string;
  authorUid: string;
  votes: number;
  votedBy: string[];       // uids — prevents double-voting
  groupId: string | null;   // for AI grouping (SHOULD)
  groupTitle: string | null;
  createdAt: string;
};
```

### `actions`

```typescript
type ActionStatus = "open" | "in_progress" | "done" | "carried_over";

type Action = {
  id: string;
  retroId: string;
  cardId: string | null;    // source card, if converted
  teamId: string;
  title: string;
  description: string;
  status: ActionStatus;
  assigneeUid: string | null;
  deadline: string | null;   // ISO date
  createdAt: string;
  updatedAt: string;
};
```

### `conversations` (existing)

Already built. Used by AI Chat Sidebar (COULD HAVE). No changes needed.

## Data Flow

```
Browser -> AuthProvider (Firebase JS SDK) -> getIdToken()
        -> fetch("/api/retros/...", { Authorization: Bearer <token> })
        -> API route -> requireUser() (firebase-admin verifyIdToken)
        -> service layer -> MongoDB (via getDb())
        -> response: { data } or { error }

AI flow:
        -> /api/retros/[id]/ai/summarize
        -> retro-ai.service.ts -> collects all cards
        -> callAiProxy() (existing) -> structured prompt
        -> AI returns JSON: { themes[], suggestedActions[] }
        -> response: { data: { themes, suggestedActions } }
```

## API Routes

All routes behind `requireUser()` from `src/lib/api/auth.ts`.

### MUST routes

- `POST /api/retros` — Create retro (title, template, votesPerUser)
- `GET /api/retros` — List user's retros (by createdBy uid)
- `GET /api/retros/[id]` — Get retro with phase info
- `PUT /api/retros/[id]` — Update retro (advance phase)
- `POST /api/retros/[id]/cards` — Add card to column
- `GET /api/retros/[id]/cards` — List all cards for retro
- `POST /api/retros/[id]/cards/[cardId]/vote` — Toggle vote on card
- `POST /api/retros/[id]/actions` — Create action (from card or manual)
- `GET /api/retros/[id]/actions` — List actions for retro
- `PUT /api/actions/[id]` — Update action (status, assignee, deadline)
- `POST /api/retros/[id]/ai/summarize` — AI analyzes all cards, returns themes + suggestions

### SHOULD routes

- `GET /api/actions` — Team Board: all open actions across retros
- `POST /api/retros/[id]/ai/group` — AI clusters cards, returns groupId + groupTitle suggestions
- `GET /api/retros/[id]/carry-over` — Fetch open/failed actions from previous retro in same team

## Component Architecture

### Retro Board Page (hero screen)

- **PhaseBar** — Shows current phase via `Steps` or `Segmented`. Moderator sees "Next Phase" button.
- **ColumnLayout** — 3-column grid: Mad (red) | Sad (blue) | Glad (green)
- **CardList** — Renders cards per column, sorted by votes in vote/actions phase
- **StickyCard** — Ant Design `Card` with colored left border. Shows content, vote count, vote button (vote phase), "Convert to Action" button (actions phase)
- **AddCardForm** — Text input + submit. Visible only in `write` phase.
- **AiSummaryPanel** — Displayed in `actions` phase. Shows AI-generated themes and suggested actions. "Accept" button creates action items.

### Team Board Page (SHOULD)

- **CarryOverBanner** — Alert showing open actions from previous retro
- **ActionTable** — Ant Design `Table` with status, assignee, deadline columns. Filterable by status.
- **ActionCard** — Compact card with status badge, assignee avatar, deadline tag

### Action Creation Modal

- **CreateActionModal** — Ant Design `Modal` with form: title, description (pre-filled from card), assignee (`Select`), deadline (`DatePicker`), status

### Ant Design Component Mapping

- `Card` — Sticky notes (colored border per column)
- `Button` + `Badge` — Voting interaction
- `Steps` or `Segmented` — Phase indicator bar
- `Table` — Team Board action list
- `Modal` — Action creation
- `Select` + `DatePicker` — Assignee + deadline in modals
- `Drawer` — AI chat sidebar (COULD HAVE)
- `Alert` — Carry-over banner
- `Empty` — Empty states for boards with no cards/actions
- `Spin` — Loading states

## AI Integration Strategy

All three AI features reuse `callAiProxy()` from `src/services/ai-chat.service.ts`. The only new code is prompt engineering.

### 1. AI Summarize (MUST)

Collects all cards from a retro, formats them as a structured prompt, sends to AI. System prompt instructs AI to return JSON:

```json
{
  "themes": [
    { "title": "CI/CD Issues", "cardIds": ["...", "..."], "summary": "..." }
  ],
  "suggestedActions": [
    { "title": "Add pipeline cache", "description": "...", "relatedTheme": "CI/CD Issues" }
  ]
}
```

### 2. AI Grouping (SHOULD)

Same approach — sends cards, asks AI to return groups with titles and card assignments.

### 3. AI Chat Sidebar (COULD)

Frontend chat UI connecting to existing `/api/ai/chat` endpoint. Injects retro context (cards + votes) as the first user message so the AI has board awareness.
